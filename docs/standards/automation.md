# GitHub delivery automation

- CI runs policy, quality, integration, mobile and containers on every PR/push to develop/main. The required aggregate fails on any unsuccessful gate. Each observed job is required with Actions provider and strict branch freshness; no path filters bypass checks.
- Policy includes actionlint 1.7.12 (verified release checksum) and offline zizmor 1.30.1. Local-action and exact pnpm-bootstrap exceptions are narrowly documented inline. Read-only checkout credentials are not persisted; jobs have explicit timeouts.
- Quality uses cached workspace lint/types/unit tests, plus root scripts and the architecture checker. Turbo caches are branch-isolated by GitHub and keyed by job/commit. Full checks remain enabled. Integration builds API/web and verifies real Postgres fresh/repeat migrations; mobile-js builds both Metro bundles, mobile-native compiles Android/iOS, and the required mobile aggregate rejects failed/skipped platform builds. Live checks are uncached.
- CODEOWNERS requires the maintainer team. Preserve the deliberately requested develop-quality bypass; never use it to hide a failure. Ticket branches, one-line imperative Conventional Commits, Linear/spec/evidence links and current develop ancestry remain mandatory. Develop alone releases into main; release merges preserve ancestry.
- Containers on PRs build/test disposable images without publishing. On pushes, build and push multi-architecture SHA candidates once, or reuse existing SHA digests on a retry. Test both linux/amd64 and linux/arm64 by immutable digest and verify the revision label. Official main publication waits for all required checks. A failed candidate is never officially released.
- Candidate images have OCI source/revision labels, explicit maximal provenance, SBOMs and GitHub attestations. Docker caches accelerate builds; no rebuild happens during release or promotion. Verify real pushed attestations with `gh attestation verify oci://IMAGE@DIGEST -R OWNER/REPO` after the first push pipeline; PR checks do not establish registry attestations.
- Main alone calculates one workspace SemVer and changelog from shipped non-merge commits. During 0.x, breaking changes bump minor; otherwise breaking changes bump major. Features bump minor and other shipping commits bump patch. Graduation to 1.0 requires an explicit reviewed policy decision. Manifests remain package version placeholders; Git tags/releases identify shipped versions.
- Publication creates a draft with the tested digest manifest, refuses any existing version/manifest mismatch, adds aliases without overwriting different digests, then publishes the release. Retries reuse the same SHA candidates and validate existing release metadata. No bot commit writes changelogs to protected main. CI publication is part of the branch's push workflow, not a default-branch workflow_run handler.
- QA promotion runs after an official main release; production waits for environment approval and validates both current QA aliases against the release manifest before any write. Manual production dispatch cannot bypass this digest prerequisite. Aliases identify environments; main/develop are branches. Registry retagging is not AWS deployment.
- Required production review forbids self-review/admin bypass. Version tags cannot be updated/deleted. Restricting tag creation awaits an identified dedicated release App; GITHUB_TOKEN can currently create releases.
- Audit JSON and a visible severity summary accompany quality checks. Critical findings fail; known high/moderate chains remain visible and tracked in dependency-security.md. Audit failures do not masquerade as a zero-findings report. CI artifacts expire after 7 days; release-manifest run artifacts after 30 days, while the release asset is retained.
- Weekly Dependabot proposals update pnpm/framework groups (Dependabot uses the npm ecosystem identifier) and SHA-pinned Actions, with a 7-day normal-update cooldown. Proposal PRs intentionally fail ticket/spec merge policy until adopted into a new Linear ticket with `pnpm run deps:adopt PR_NUMBER WEA-N`. That helper verifies author/repository/file scope, branches from develop and prepares unconfirmed scenario artifacts plus a local ignored patch. After agreement, `pnpm run deps:adopt PR_NUMBER WEA-N --apply` checks the ticket state before applying it. It does not commit/push/merge or waive checks. Confirm scenarios, verify the update, then open the normal reviewed ticket PR. Never reuse WEA-6 for future updates.

AWS runtime integration, native signing/device/store validation and Linear release API integration remain separate environment work. No release or deployment is claimed from PR validation alone.

## Main release queue limitation

The current main concurrency group retains one running and one pending workflow. A later merge can replace an older pending run. Those changes remain in Git and ship in the next successful release, but the replaced commit receives no individual release/tag. Avoid burst merges when a release for each main commit is required. R8 is a maintainer decision: retaining batching is recommended for the current develop-to-main release flow; no concurrency policy change has been made.

[Current GitHub documentation](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency) also supports `queue: max` (up to 100 pending runs; incompatible with cancel-in-progress true). This is a further R8 option for main; queue order follows when runs begin waiting and is not a guarantee of dispatch/commit order. Any adoption must preserve release ordering and be validated with supported workflow tooling. It is not enabled by this remediation.
