# Choosing a spec-driven development workflow

## Recommendation and decision criteria

Prefer **Spec Kit** for Weave's greenfield setup and explicit constitution requirement. Choose **OpenSpec** instead if a lighter iterative change process is the higher priority. Both can describe NestJS, Next.js, Prisma, and future React Native work; neither replaces framework-specific standards, tests, linting, dependency-boundary checks, or code review. Do not install multiple competing lifecycle systems initially.

Before adopting one, run a small feature through the proposed lifecycle and assess artifact clarity, review effort, and whether acceptance criteria map to meaningful checks. Record the selection in an architecture decision record. Pin the selected tool release, review generated files, and configure only the coding agents actually used. Current invocation syntax differs by integration: older tutorials can show obsolete commands. Verify the pinned release's own docs during setup.

Define a durable-spec policy explicitly: who reviews requirements, how changed behavior updates existing specs, how tasks reference acceptance criteria, and what evidence closes a task. Decide proportionate treatment for defects, documentation, and maintenance; a spec process should not turn a typo fix into a product-design exercise.

## What is standard practice?

Requirements, acceptance criteria, design decisions, traceability, and tests are established engineering practices. These named AI-agent toolkits are newer implementations of that intent, not a universally required industry standard. The maintainers' documentation demonstrates their processes and support; it does not establish independent comparative effectiveness or industry-wide adoption. Avoid selecting based on stars or claims of universal productivity gains.
