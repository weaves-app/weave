# Android implementation evidence — WEA-29

This lane implements Android T033/T035, Android T038/T039/T041, automated T044/T047/T048, T050/T052 and Android T054/T055. Provider and physical-device acceptance remain open by the user's explicit decision. No production calls, provider configuration, commits or pushes were performed.

## Implemented boundaries

- `ClerkSessionAuthorizedTransport.kt` captures the native validated session and native auth epoch separately from notification intent generation, obtains `Session.fetchToken(GetTokenOptions())` through native Clerk, rechecks authority before dispatch/acceptance, uses fixed HTTPS paths, disallows redirects, bounds token and HTTP work separately to five seconds, and caps decoded response bodies at 16 KiB.
- `ClerkAuthService` independently observes native invalidation even without a JS subscriber. Sign-out suppresses notification authority before suspended SDK work. Benign same-session emissions preserve authority; real A→B→A transitions fence stale credentials.
- `NotificationCoordinator` serializes SDK mutations, retires the previous account before waiting on a replacement grant, validates short-lived grants, uses signed login/update-JWT only, suppresses stale foreground eligibility immediately, and keeps explicit opt-in separate. It does not call optOut during acquire, Reload or ordinary auth suspension. Current signed-binding evidence is separate from a restored SDK external ID.
- One process initializes SDK and owns observers; React bridge consumers only attach/detach their event subscriptions. Matching root leases and a per-lease intent high-water mark fence stale work. Readiness uses a constant-space per-lease positive-decimal attempt high-water mark, revision correlation and elapsed native monotonic duration; no absolute native clock or private provider identity crosses JS.
- Native permission/settings calls occur only through explicit Enable/settings. Android 13+ uses public OS rationale plus the SDK's persisted `canRequestPermission`; privileged hidden PackageManager permission flags are not accessed. Earlier Android versions never invent a runtime prompt. Real device-managed restriction classifications remain a device acceptance limitation.
- `NotificationPresentationAdapter` leaves eligible SDK events untouched (one default display) and prevents ineligible display without reading payloads. No RN-wrapper foreground/click listener is installed by authored code.
- The actual installed SDK launch helpers are exercised with the actual merged manifest metadata. HTTPS and custom-scheme launch URLs are suppressed and the ordinary app launch intent survives. No payload navigation queue exists.
- SDK log and alert levels are NONE before initialization. Responses/events contain allowlisted sanitized fields only. Strict whole JSON response decoding rejects trailing data and unknown grant/readiness keys.

## Configuration and installed SDK

`apps/mobile/android/app/build.gradle` reads public build variables `ONESIGNAL_APP_ID` and `NOTIFICATIONS_API_ORIGIN` into BuildConfig. Missing/invalid config leaves notifications unavailable without crashing auth. The origin must be HTTPS with no credentials, path other than `/`, query or fragment. Composition lives in `NotificationDependencies.kt`, called from `MainApplication.onCreate`.

The SDK default icon is `app/src/main/res/drawable/ic_stat_onesignal_default.xml`. The installed SDK's default channel is `fcm_fallback_notification_channel` with label `Miscellaneous`. There is no promised custom channel label. Manifest `com.onesignal.suppressLaunchURLs` is Boolean true; `com.onesignal.NotificationOpened.DEFAULT` remains absent.

RN OneSignal 5.5.15 resolves modular native OneSignal 5.10.2. `onesignal.disableLocation=true` remains set in `android/gradle.properties`. Native Kotlin compiles against actual `initWithContextSuspend`, signed `loginSuspend`, `updateUserJwtSuspend`, `logoutSuspend`, JWT invalidation, user/push/permission observers and foreground listener APIs. IV logout uses the SDK's separate identity suspension behavior, preserving explicit opt-in preference; actual provider IV enforcement remains unverified until setup/device acceptance.
