## Source/API mappings and important SDK constraints

- `authentication/infrastructure/clerk-session-authenticator.ts` uses installed `@clerk/backend@3.23.0` `createClerkClient().authenticateRequest()` with `acceptsToken: 'session_token'`, configured `jwtKey` and zero clock skew. A fresh Request contains only the supplied bearer, so cookies cannot authenticate the request. Subject/session/token expiry come exclusively from verified claims. The guard exports that result through a symbol-owned request slot.
- Installed `node_modules/@clerk/backend/dist/api/endpoints/SessionApi.d.ts` exposes `getSession(sessionId: string)` with no AbortSignal/timeout argument. The backend Session resource has `id`, `userId`, `status` and timing fields, **no** frontend `tasks`/`currentTask` property. The adapter therefore performs a fixed HTTPS GET to `/v1/sessions/<encoded verified sid>` with the configured secret and a five-second abort, validates raw `id`, `user_id`, `status` as unknown data, and never patches global fetch. No retries, caller-controlled URL or caller-directed key discovery.
- [Clerk's official task documentation](https://clerk.com/docs/guides/development/custom-flows/authentication/session-tasks), checked 2026-10-17, specifies that incomplete tasks leave the session pending and completion changes it to active. Thus the required fresh live `status === 'active'`, alongside token pending rejection, is the documented available completion signal. No nonexistent backend task property is invented. Token status alone is insufficient; a live pending/revoked/ended/expired/unknown session is rejected.
- `notifications/infrastructure/jose-identity-grant-signer.ts` dynamically imports exact `jose@6.2.12` through the unchanged API TypeScript configuration. Tests verify the emitted runtime, not only tsx. Claims are only `iss`, `exp`, and `identity.external_id`; no client-provided or profile claims. Expired bearer is 401 at authentication; still-valid bearer with fewer than 15 whole seconds when signing is 503 with retry 5.
- `notifications/infrastructure/onesignal-readiness-reader.ts` calls only `https://api.onesignal.com/apps/<configured app>/users/by/external_id/<verified account>`. Authorization is the server-minted identity JWT; no OneSignal API key. Only successful JSON is streamed/parsed, bounded at 1 MiB. Non-success bodies are canceled unread; 404 becomes pending; 429 persists numeric/date Retry-After before returning bounded guidance; other failures become unavailable. No provider profile/token escapes the boolean result.
- `postgres-request-budget.ts` uses a dedicated application-singleton pg pool injected through `BudgetDatabase`. This keeps advisory transaction/timeout control explicit without exposing Prisma or pg contracts to application use cases. Pool shutdown is wired to module destruction; connect/query timeouts are five seconds and lock timeout two seconds. Reservations use database time after an advisory lock, reject without queuing future slots and do not extend retention on rejection. Account rows expire 24 hours after cooldown, global rows never expire. Cleanup reserves a durable 60-second app lease before deleting at most 100 eligible rows, with row locks/rechecks and no drain loop. Safe cleanup failure does not undo the already accepted account request.
- `notification-http.ts`, `notification-input.ts` and `notifications.controller.ts` own HTTP policy. Both routes return no-store; strict caller fields/query are rejected before use cases; failures contain safe codes plus optional matching 1–60 second retry metadata. `VerifyReadiness` shares only simultaneous identical captured contexts, deletes settled promises and returns no completed positive cache.

## Environment setup and remaining acceptance

Server variables (supply through the deployment's secret/configuration mechanism; never commit values):

| Variable                         | Requirement                                                                                                                               |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `DATABASE_URL`                   | PostgreSQL for committed migrations and shared request budgets.                                                                           |
| `CLERK_SECRET_KEY`               | Same Clerk instance as native; server-only, permits live session lookup.                                                                  |
| `CLERK_PUBLISHABLE_KEY`          | Same Clerk instance; required by backend SDK configuration.                                                                               |
| `CLERK_EXPECTED_ISSUER`          | Exact trusted HTTPS instance issuer.                                                                                                      |
| `CLERK_JWT_KEY`                  | Trusted Clerk public PEM key. Required to avoid network key discovery/retries; update configuration on key rotation.                      |
| `CLERK_ALLOWED_ORIGINS`          | Optional comma-separated origins. Any present token azp must match; absent azp native bearer remains allowed.                             |
| `CLERK_AUDIENCE`                 | Optional expected audience; if configured, token must contain it.                                                                         |
| `ONESIGNAL_APP_ID`               | Canonical lowercase UUID, same environment/app as native.                                                                                 |
| `ONESIGNAL_IDENTITY_PRIVATE_KEY` | Server-only PKCS8 ES256 signing PEM for configured OneSignal identity verification.                                                       |
| `NOTIFICATION_BUDGET_HMAC_KEY`   | Dedicated stable secret of at least 32 characters shared by replicas. Rotation changes account quota scopes; coordinate it operationally. |

OneSignal API keys are neither needed nor accepted by this feature. Apply committed migrations with `pnpm --filter @weave/api run db:deploy` against the intended authorized environment. One-shot maintenance: `pnpm --filter @weave/api run notifications:cleanup` with `DATABASE_URL` and `ONESIGNAL_APP_ID`; prints only aggregate deleted count and respects the same 100-row/60-second limits. No scheduler is installed. Missing notification/Clerk configuration fails requests safely while ordinary health remains available.

The disposable local fixture is PostgreSQL under `/private/tmp/wea29-postgres`, bound only to `127.0.0.1:55449`, personal local user `weave`, test database `wea29_verify`. Server log is `/private/tmp/wea29-postgres.txt`. It remains running for parent verification. Tests refresh/delete only their synthetic scoped records. No external database was touched.

Still unverified by this code work: provisioned OneSignal identity verification/app-wide enablement and key compatibility; live Clerk key/issuer/audience/environment configuration; APNs/FCM credentials and platform registrations; real native HTTPS origin connectivity; targeted notification delivery; physical Android/iOS logout and account-switch behavior; device/private-log review.
