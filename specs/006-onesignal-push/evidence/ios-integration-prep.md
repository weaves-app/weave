# iOS integration preparation — read only

Checked 2026-10-17 against installed React Native OneSignal 5.5.15, official tagged iOS SDK 5.8.0 source, vendored Clerk 1.6.0, and the current Weave source. This report implements no notification behavior or provider configuration. T050 is Android; the matching iOS lifetime task is T051.

## Composition decision for T041

The installed RN wrapper has an unconditional `UIApplication` launch swizzle. Its launch handler calls `RCTOneSignal.initOneSignal`, which initializes OneSignal with a nil app ID. The exact native SDK restores a cached app ID when this input is nil. Consequently, skipping our configured initialization when public configuration is absent would not reliably disable setup on an upgraded installation. The wrapper category has no compile-time/environment opt-out in this release. Its separate event emitter also exposes raw subscription tokens and notification payloads if used.

Use the following later composition change, preserving the npm pin for Android:

```javascript
// apps/mobile/react-native.config.js — framework-required CommonJS boundary
module.exports = {
  dependencies: {
    'react-native-onesignal': {platforms: {ios: null}},
  },
};
```

No React Native config file currently exists. The installed CLI 20.1 schema explicitly permits this shape; a read-only schema validation passed. Add `ENV['ONESIGNAL_DISABLE_LOCATION'] = 'true'` before dependency resolution in the Podfile and explicitly add `pod 'OneSignalXCFramework/OneSignal', '5.8.0'` inside the existing `Weave` target. Do not include the RN iOS pod, aggregate/default pod, Location, or InAppMessages. The modular core transitively includes Core, OSCore, Outcomes, Extension, Notifications, User, and LiveActivities; those frameworks do not imply an authored NSE or Live Activity feature.

Only the native process runtime performs configured initialization, once, after validating a UUID app ID and fixed HTTPS backend origin. Set console and alert levels to `.LL_NONE` before initialization and identity calls. Preserve the SDK's ordinary native push delegate integration; removing the RN wrapper is different from disabling native SDK push swizzling.

Audit the final RN CLI configuration, Podfile.lock and linked binary. The existing Info.plist contains an unused empty `NSLocationWhenInUseUsageDescription`; remove it during no-location configuration. Add actual push entitlements/capability, background `remote-notification`, and Boolean `OneSignal_suppress_launch_urls = true`. Keep minimum iOS 17 and current New Architecture. No NSE/App Group or provider credentials are introduced.

Swift concurrency caution: the Objective-C SDK callback protocols are not MainActor contracts. Async observer/JWT work can hop to the process actor. Foreground suppression cannot wait for such a hop: the SDK immediately displays after callbacks return unless prevented. Use a small synchronous thread-safe eligibility snapshot for that callback, updated by native authority/coordinator transitions. Retain one listener set across React root replacement; stale release cannot remove newer ownership.

## Captured Clerk authority for T034/T036

The installed public API is `try await capturedSession.getToken(.init()) -> String?`, with defaults `template: nil`, `expirationBuffer: 10`, `skipCache: false`. Capture the actual `Session` while validating current ownership. Do not call `Clerk.shared` before configuration: debug builds assert. Composition should inject the configured Clerk object through the existing runtime.

The native public checks are `clerk.session?.id`, `session.user?.id`, `session.status == .active`, `(session.tasks ?? []).isEmpty`, and `clerk.isAuthFlowComplete`. Existing fresh auth validation also performs the Keychain health check and `clerk.refreshClient()`. Notifications must consume the existing validated authority without independently starting authentication or adding a refresh loop.

Important: a captured Session is insufficient protection. Vendored token fetching searches all active sessions, and may return a fetched token even when accepting it into the current cache fails. Explicitly recheck current selected session/account and a native validated-authority epoch before token acquisition, before HTTP, and before accepting any completion. A→B→A rejects old epoch even if IDs match again. Notification runtime generations are independent of the auth controller's generations; do not compare them as if they share a counter.

`ClerkAuthService` currently keeps generation/epoch/validated-active state privately. Its `onSnapshot` and the provider's `invalidationHandler` are single callbacks. Do not overwrite them to add notifications. Publish a native consumer-owned authority reader/subscription seam that invalidates at pending sign-out/authentication/dispose/native revocation and publishes only after task-free validated success. Return an opaque captured native authorization handle; it owns token access and current checks. Keep root lease/notification intent generation in the process coordinator as a separate guard.

Proposed later names: `NotificationSessionAuthority`, `CapturedNotificationSession`, `NotificationTokenAccess`, `ClerkSessionAuthorizedTransport`, `NotificationHTTPClient`, `NotificationMonotonicClock`, `NotificationDeadline`. `NotificationSessionContext.generation` remains notification-intent generation. Native authority epoch is not supplied by JS.

Sources: repository `Weave/Auth/{ClerkProvider,ClerkAuthService,WeaveAuthRuntime,SessionAuthorizedTransport}.swift`; vendored `ClerkKit/Core/Clerk.swift`, `Clerk+AuthFlow.swift`, `Domains/Auth/Session/{Session,SessionTokenFetcher}.swift`, and `Identity/ClerkIdentityController+SessionTokens.swift`; JS `features/notifications/notification-runtime.ts`.

## HTTP and coordinator seams

Keep `SessionAuthorizedTransport.execute(context:operation:)` allowlisted to identity-grant and readiness. Origin/path come only from validated native config; JS cannot choose URL, previous account, headers, or token. Use HTTPS, ephemeral URLSession, no cookie authority/cache, and a delegate that rejects all redirects. Apply the 16 KiB cap to decoded streaming bytes for both success/error responses before JSON parsing; `data(for:)` followed by a size check is too late.

Token and HTTP stages have separate five-second deadlines. A structured task-group race can wait for a noncooperative child after cancellation. Clerk's shared token task may outlive a caller's cancellation. A deadline seam therefore must resolve the caller once at the deadline, reject late results, and cancel the underlying operation where supported without waiting for it to finish. Test this through controlled deferred token/HTTP completions rather than sleeps or live services.

Proposed `NotificationCoordinator` owns one desired account-or-signed-out intent, a process-local epoch, active root lease, one observer set, one in-flight setup attempt and serialized SDK identity commands. Validate grant account/shape/expiry natively; keep its JWT exclusively native. Wrong-account JWT callbacks are ignored. Duplicate current callbacks coalesce; short-validity/failing grants do not immediately reissue. On sign-out, invalidate local readiness immediately and request supported SDK cleanup without awaiting network. After any already-dispatched obsolete SDK command, observe/reconcile to current intent.

Readiness retains exact native subscription/account/revision. Record native monotonic request start before HTTP, cap deadline by start + 60 seconds and server duration, and emit only matching attemptId with integer remainingValidityMs in 0–60000. No absolute native clock crosses the bridge; duplicate callbacks cannot extend an existing proof. SDK local observer changes are invalidation signals, never server acknowledgement.

## Bridge wiring for T038

Preserve codegen name `WeaveAuthSpec`, package mapping, and WeaveAuth module. The generated umbrella already contains `NativeWeaveNotificationsSpec`, `NativeWeaveNotificationsSpecBase`, `NativeWeaveNotificationsSpecJSI`, and `emitOnNotificationChanged`. The generated provider map currently contains only WeaveAuth; add `ios.modules.WeaveNotifications.className = 'WeaveNotificationsModule'` in package codegen configuration and regenerate normally, never edit generated files.

Mirror the existing Auth bridge with `@objc(WeaveNotificationsEngine)`, `execute:payload:completion:`, and `onNotificationChanged`; Objective-C++ `WeaveNotificationsModule` derives from `NativeWeaveNotificationsSpecBase`, exports `WeaveNotifications`, uses main-queue setup, returns `NativeWeaveNotificationsSpecJSI`, and forwards only sanitized JSON via `emitOnNotificationChanged`. Route operations through a strict parser and injected `NotificationExecuting`/coordinator contract.

The only operations are acquire/release/reconcile/enable/refresh/openSettings. Require versioned envelopes, root lease/generation and operation-specific fields; readiness additionally has attemptId/revision. Reject unknown fields/operations, malformed or Boolean-as-integer values, stale leases and out-of-range counters before any effect. Observation output is only lease/generation/revision/permission/canRequest/registrationPresent/enabled/matchesCurrentAccount. Readiness output is only its correlated safe status/duration/retry guidance. No SDK JSON representation, raw notification, subscription ID/token, external ID, or credential crosses this boundary. Final signed-out envelope generation details must be synchronized with the JS gateway since its null-context port has no generation argument.

## T045/T051/T054 caveats and evidence

The SDK checks Bundle.main's `OneSignal_suppress_launch_urls` before launching a URL. Its click listener registration replays buffered clicks. The unhosted native test runner has a generated plist distinct from the application plist; tests must not assume the app key automatically appears in the runner. Test launch policy/actual built plist deliberately, then keep cold/warm device URL-escape cases open until executed. A no-op listener must remain no-op after authentication, so buffered or old-account payloads cannot become routing instructions.

Logging level NONE suppresses SDK console/modal output, but not every diagnostic sink. Exact 5.8.0 `OneSignalLog` forwards to all OSLogListeners and the optional internal remote sink regardless of local level. The remote sink can be enabled by cached/provider `logging_config.log_level`; no public app-side disable was found in the inspected public surface. `updateUserJwt` emits a token suffix at verbose level. Therefore NONE alone is not proof of SDK diagnostic redaction. Avoid adding log listeners, verify provider remote logging configuration for controlled acceptance, and preserve this as a T054 audit concern requiring an explicit tested mitigation if the strict policy includes every SDK diagnostic sink. Do not change provider configuration or private SDK internals as part of this read-only report.
